KV cache e batching

Na semana 6, um pedido sozinho. Aqui, o servidor: muita gente ao mesmo tempo, uma GPU só. Esta página mostra por que o lote sai barato, o que limita o tamanho dele (a memória do KV cache) e as quatro técnicas que todo runtime moderno usa para encher o lote sem travar ninguém.

01

O lote: ler os pesos uma vez, servir a todos

No decode, cada passo traz todos os pesos da memória para gerar um token. Com vários pedidos no mesmo passo, os pesos viajam uma vez e multiplicam os vetores de todos. As contas a mais quase não custam, porque o processador estava esperando a memória. Mexa no tamanho do lote.

02

KV cache: a memória de cada pedido

Os pesos são de todos; o KV cache é de cada um: 2 × camadas × cabeças KV × dimensão × bytes por token. A memória que sobra depois dos pesos é o que decide quantos pedidos cabem no lote. Compare reservar o contexto máximo para cada pedido com guardar só o que foi usado, em blocos.

03

PagedAttention: o cache em blocos

O truque da memória virtual: o KV cache de cada pedido é cortado em blocos de tamanho fixo (aqui, 4 tokens; no vLLM, 16). Cada pedido tem uma tabela de blocos que diz onde cada pedaço está. Os blocos não precisam ser vizinhos, e só o último de cada pedido tem sobra.

04

Batching estático × contínuo

Respostas têm tamanhos diferentes. No batching estático, o lote só sai quando o pedido mais longo termina, e as vagas de quem já acabou ficam paradas. No batching contínuo, o escalonador remonta o lote a cada passo: quem terminou sai, quem esperava entra.

05

Chunked prefill: prompt longo em pedaços

20 pedidos estão escrevendo quando chega um prompt enorme. Sem cortar, o prefill dele vira um passo gigante e todo mundo congela. Com chunked prefill, o prompt é dividido: cada passo leva os decodes e um pedaço do prompt, até um orçamento de tokens. Llama-3.1-8B FP16 numa RTX 4090.

06

Prefix caching: começo igual, cache igual

O K e o V de um token só dependem dele e dos tokens anteriores. Se vários pedidos começam com o mesmo prompt de sistema, o cache desse começo é idêntico: calcula uma vez e todos apontam para os mesmos blocos. Só blocos cheios (16 tokens) são compartilhados.

Fixo no começo, variável no fim

O servidor dá a cada bloco cheio uma impressão digital (hash) dos seus tokens e de tudo o que veio antes. Pedido novo: procura os hashes dos primeiros blocos e reaproveita os que já existem.

Por isso, basta um token diferente no início (a data, o nome do usuário) para nenhum bloco depois dele bater.

Ganha duas vezes: menos contas no prefill (o 1º token sai antes) e menos memória de KV (cabem mais pedidos no lote).

07

A resposta

Os pesos viajam uma vez por passo

O lote divide a viagem

No decode, o caro é trazer os pesos da memória. Com 20 pedidos no passo, os pesos são lidos uma vez para 20 tokens. As contas extras usam um processador que estava ocioso.

O que cresce é o KV cache

A memória limita o lote

Cada pedido tem o seu cache. PagedAttention tira o desperdício da reserva, prefix caching compartilha o começo igual: cabem mais pedidos.

A agenda mantém o lote cheio

Ninguém espera à toa

Batching contínuo troca pedidos a cada passo. Chunked prefill corta prompts longos para ninguém congelar.
