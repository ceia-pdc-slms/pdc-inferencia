Escala: 16 degraus para qualquer peso

INT4 só tem 16 valores: −8 a 7. Para guardar pesos como 0,12 ou −0,31, cada grupo de pesos ganha uma escala: o maior peso do grupo vira 7 e o resto é proporcional. Todo LLM tem alguns outliers, pesos muito maiores que os outros. Aumente o outlier e veja os pesos pequenos sumirem.

O que acelera: o mesmo INT4, três velocidades

Todas as multiplicações por pesos de um passo do Qwen2.5-0.5B (24 camadas e o lm_head), no ONNX Runtime, com 4 núcleos. Menos bytes só viram velocidade quando o kernel, o código que faz a multiplicação, sabe trabalhar com eles. E só no decode: no prefill, quem limita são as contas.

A conta do tok/s: onde o ganho some

Um token custa duas coisas: trazer os pesos (encolhe com a quantização) e todo o resto: atenção sobre o KV cache, normalizações, escolha do token, o próprio runtime (não encolhe). O ponto de partida é o que medi: 29 ms de resto com prompt curto, mais 25 µs por token de contexto.

06

A resposta

1 · Os bytes caem menos que o nome

4 bits não são 4 bits

As escalas somam 0,5 bit por peso, e a matriz de saída fica em 8 bits. Do F16 para o Q4_0, o nome promete 4× e cada token lê só 2,9× menos.

2 · O kernel decide

Menos bytes, mais trabalho

Cada peso precisa ser desempacotado. Com conta inteira, o INT4 foi 5,6× mais rápido; desempacotando para FP32, 2,5×; com um kernel sem otimização, 20× mais lento.

3 · O resto não encolhe

29% a 63% do token

Atenção, KV cache, normalizações e o runtime não mudam com o formato dos pesos. Quanto maior o contexto, menor o ganho.
